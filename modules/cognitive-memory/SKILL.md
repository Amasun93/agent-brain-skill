# Cognitive Memory Skill

**认知记忆系统**：专属理解用户的3D认知架构

---

## 一、架构总览

### 3D认知矩阵

```
                    PromptX (横切轴: 信息是什么)
                          ↓
            X1知识 ─── X2方案 ─── X3经验 ─── X4参考
                         ↑
    ┌────────────────────┼────────────────────┐
    │                    │                    │
    ↓                    ↓                    ↓
  L1 状态            L2 情境              L3 行为
(实时变化)         (事件记录)           (行为模式)
    │                    │                    │
    └────────────────────┼────────────────────┘
                         ↓
              RoleX (提炼轴: 怎么从浅到深)
         encounter → reflect → experience → realize
                         ↓
                       L4 认知
                    (价值观信念)
                         ↓
                       L5 核心
                    (底层驱动力)
```

### 提炼循环：认知层的反思机制

**核心理念**：认知层不仅是"描述性"的——记录你是谁、怎么想、怎么做；它还应该是"反思性"的——主动审视这些认知本身是否正确、是否需要更新。

提炼循环是嵌入认知层的自我反思机制。它不追求"记住更多"，而是追求"理解更准"。

**核心三问**：

```
① 有没有新的认知信号？  →  ② 和现有认知矛盾吗？  →  ③ 值得更新吗？
这次对话中有没有新的       新信号和已有记录         证据够吗？
行为模式、偏好、价值观       有冲突吗？             触发阈值到了吗？
```

### 三轴职责

| 轴 | 解决什么问题 | 操作频率 |
|----|-------------|---------|
| **纵深轴(五层)** | 信息放在哪 | 写入时决定 |
| **横切轴(PromptX)** | 信息是什么 | 分类时决定 |
| **提炼轴(RoleX)** | 信息怎么深化 | 定期触发 |
| **反思轴(提炼循环)** | 认知是否需要进化 | 每次深度对话结束 |

## 二、提炼循环详细规范

### 2.1 触发时机

**触发提炼循环的场景**：

| 触发条件 | 描述 | 优先级 |
|---------|------|--------|
| **深度对话结束** | 一次有意义的对话（非闲聊），产生了新的认知信号 | 高 |
| **用户明确指令** | 用户说"记住"、"记一下"、"更新一下" | 高 |
| **检测到认知矛盾** | 新信号与现有认知存在明显冲突 | 高 |
| **定时触发** | Calendar 周任务时批量扫描待验证队列 | 中 |

**不触发的场景**：

- 单次闲聊（无实质信息）
- 纯查询性对话（用户只是问问题，没有表达自我）
- 情绪性爆发（愤怒、激动时的表达，可能不反映真实偏好）

### 2.2 操作流程

#### 第一步：新信号检测

**检查维度**：

```
┌─────────────────────────────────────────────────────────────┐
│  新信号类型                                                 │
├─────────────────────────────────────────────────────────────┤
│  • 行为模式：遇到X时会做Y（之前未观察到）                   │
│  • 偏好表达：对X的喜好/厌恶（之前未记录）                    │
│  • 价值观流露：提到"我觉得应该X"（与现有价值观一致或矛盾）  │
│  • 决策倾向：选择A而不是B（揭示了优先级）                   │
│  • 自我认知：用户对自己的评价（可能有参考价值）              │
└─────────────────────────────────────────────────────────────┘
```

**信号质量判断**：

```
✗ 一次性情绪 → 不记录为信号
✗ 情境性表达 → 降级记录，标记情境
✓ 跨情境一致 → 可能是真实信号
✓ 多次提及   → 高置信度信号
```

#### 第二步：矛盾检测

**检测范围**：检查新信号是否与 `brain/00-共享认知/` 下的已有记录矛盾：

```
brain/00-共享认知/
├── behavior.md     # L3 行为模式
├── cognition.md   # L4 价值观认知
└── core.md         # L5 核心特质
```

**矛盾类型**：

| 矛盾类型 | 描述 | 处理策略 |
|---------|------|---------|
| **情境性矛盾** | 不同情境下表现不同，不算真正矛盾 | 降级表述，添加情境限定 |
| **观察性矛盾** | 两次观察结果不一致 | 进入待验证队列，分析原因 |
| **实质性矛盾** | 与核心认知直接冲突 | 标记"待验证"，不覆盖旧认知 |

**矛盾处理示例**：

```
旧认知：用户"做决策前需要3天冷静期"
新观察：用户在某次紧急情况下快速决策

判断：情境性矛盾（紧急情境vs普通情境）
处理：更新为"在非紧急情境下需要冷静期，紧急情境可快速决策"
```

#### 第三步：证据积累

**证据阈值**：

| 层级 | 证据要求 | 更新方式 |
|-----|---------|---------|
| L3 行为层 | ≥3 次独立观察 | 自动更新（标记来源） |
| L4 认知层 | ≥3 次独立观察 + 无反例 | 用户确认后写入 |
| L5 核心层 | ≥3 次独立观察 + 无反例 + 跨情境一致 | 明确确认后写入 |

**独立观察标准**：

```
✓ 不同时间点的类似行为
✓ 不同情境下的类似反应
✓ 不同对话轮次中的类似表达

✗ 同一次对话中的多次提及（算1次）
✗ 相关但不完全相同的行为（需要单独验证）
```

#### 第四步：更新决策

**决策树**：

```
新信号检测 ──→ 有矛盾？
                    │
        ┌───────────┴───────────┐
        │                       │
        ▼                       ▼
      是                       否
        │                       │
        ▼                       ▼
  进入待验证队列          证据 ≥ 3？
                               │
                    ┌──────────┴──────────┐
                    │                     │
                    ▼                     ▼
                   是                     否
                    │                     │
           ┌───────┼───────┐             继续积累
           │       │       │
           ▼       ▼       ▼
          L3      L4      L5
           │       │       │
           ▼       ▼       ▼
      自动更新   用户确认  明确确认
```

### 2.3 更新规则

#### L3 行为层更新规则

```
条件：≥3 次独立观察验证
更新方式：自动更新
更新内容：
  • 行为模式描述
  • 证据来源引用
  • 置信度标记
更新后：
  • 更新 behavior.md
  • 更新 index.md 索引
  • 追加操作日志
```

#### L4 认知层更新规则

```
条件：≥3 次独立观察 + 无反例 + 用户确认
更新方式：需要用户确认
确认方式：
  • 简单插入: "我注意到你... 这是准确的吗？"
  • 选项确认: "基于观察，你更倾向于A还是B？"
  • 延迟确认: "关于这个我有些假设，等积累更多证据再和你确认"

确认后：
  • 更新 cognition.md
  • 更新 index.md 索引
  • 追加操作日志
```

#### L5 核心层更新规则

```
条件：≥3 次独立观察 + 无反例 + 跨情境一致 + 明确确认
更新方式：需要明确确认
确认方式：
  • "我想确认一下对你的理解——你是一个X的人，对吗？"
  • 提供具体例子说明观察到的现象

确认后：
  • 更新 core.md
  • 更新 index.md 索引
  • 追加操作日志
  • 标记为"已确认核心认知"
```

### 2.4 矛盾处理策略

**核心原则**：新信号与旧认知矛盾时，**标记为"待验证"而非直接覆盖**。

```
┌─────────────────────────────────────────────────────────────┐
│  矛盾处理三原则                                             │
├─────────────────────────────────────────────────────────────┤
│  ① 不删除旧认知                                           │
│     旧认知是历史验证的积淀，不会因为一次矛盾就消失          │
│                                                              │
│  ② 不强行覆盖                                             │
│     新信号只是"可能"，不是"正确"                           │
│                                                              │
│  ③ 标记待验证                                             │
│     让新信号和旧认知并存，等待更多证据                      │
└─────────────────────────────────────────────────────────────┘
```

**矛盾登记格式**：

```markdown
---
id: PENDING-20240115-001
type: 认知矛盾
created: 2024-01-15
status: 待验证
---

## 矛盾描述

**旧认知**：用户做决策前需要3天冷静期
**新信号**：用户在紧急情况下快速决策

## 矛盾分析

可能原因：
1. 情境依赖（紧急vs非紧急）
2. 决策类型（重大vs轻微）
3. 旧认知不准确

## 待验证问题

- 是否在所有决策类型上都存在冷静期需求？
- 紧急情境是否可以打破冷静期？

## 验证进度

- [ ] 第2次验证：下次非紧急决策是否需要冷静期
- [ ] 第3次验证：下次紧急决策的反应
```

### SESSION-STATE.md 会话工作区 [v2.2新增]

**作用**：本次会话的"工作区 + 恢复层"，WAL 协议的核心载体。

**完整规范见主 SKILL.md "核心机制 1：WAL 协议"**。本节是 cognitive-memory 模块视角的补充：

#### 写入触发点

```markdown
## cognitive-memory 在哪些时点写 SESSION-STATE.md

✅ on_session_start：创建/读取 SESSION-STATE.md
✅ on_new_observation：捕获新信号时 append 一行
✅ on_contradiction_detected：检测到矛盾时 append
✅ on_evidence_accumulated：证据 +1 时 append
✅ on_session_end：会话结束时的最终状态记录

## 不写 SESSION-STATE.md 的时点
✗ 触发 lint（写入 log.md 即可）
✗ 触发 git push（不污染工作区）
✗ 触发归档（不污染工作区）
```

#### 与 index.md 的关系

| 文件 | 加载时机 | 作用 |
|------|----------|------|
| `brain/index.md` | 会话开始（始终加载） | 用户**长期**认知的索引 |
| `brain/SESSION-STATE.md` | 会话开始（WAL 恢复） | 本次会话的**临时**状态 |
| `brain/log.md` | 按需审计 | 跨会话的**操作记录** |

**三者不重复**：index 是"用户是谁"，SESSION-STATE 是"我今天在做什么"，log 是"历史上做过什么"。

| **Cursor** | ✅ 完整支持 | — |
| **纯对话 Agent** | ⚠️ 降级 | 用对话内 SESSION-STATE 提示框替代 |

### pending/ 毛坯区 [v2.2新增]

**作用**：所有新信号的"暂存区"，两阶段工作流的第一阶段。

**完整规范见主 SKILL.md "核心机制 2：先毛坯后蒸馏"**。本节是 cognitive-memory 模块视角的补充：

#### 写入触发点

```markdown
## cognitive-memory 在哪些时点写 pending/

✅ on_new_observation：检测到新信号 → 先写 pending/，**不**直接进 cognition
✅ 矛盾检测 → 矛盾条目也暂存 pending/（与 v2.1 pending.md 区分）
✅ 跨情境观察 → 写一条 pending/ 文件

## 不写 pending/ 的时点
✗ 已确认的 L3+ 提炼（直接走 promote 流程）
✗ L2 情境事件（仍写 wiki/entries/）
✗ 已被验证的旧条目（直接更新）
```

#### 写入流程

```text
新信号进来
  ↓
判断 1：是否 L2 事件？ → wiki/entries/（保持原行为）
判断 2：是否 L3+ 提炼？ → 走 governance.promote() 流程（不经过 pending/）
判断 3：是否新信号/待验证？ → pending/{日期-主题}.md ← 默认路径
  ↓
返回文件路径 + 证据计数
```

#### 最小文件规范

```markdown
---
topic: [简短主题名]
date: YYYY-MM-DD
evidence_count: 1/3
related: [cognition/behavior.md#相关条目]
status: 毛坯
---

## 观察记录
- 时间/情境/原话/后续

## 初步假设
[待验证]

## 待验证问题
- [ ]
```

**最小信息**：日期 + 主题 + ≥1 段观察。其他字段可选。

#### 与 v2.1 pending.md 的边界

| 路径 | 角色 | 何时写 |
|------|------|--------|
| `brain/pending.md` | 矛盾 / 待验证 L2+ 队列 | on_contradiction_detected 触发 |
| `brain/pending/{日期-主题}.md` | 毛坯区（所有新信号） | on_new_observation 触发 |

> **简记**：pending.md = 已认定是认知层候选；pending/ = 暂存一切新信号。

## 三、索引设计（关键挑战1）

### 主索引文件 (memory/index.md)

**始终加载，<500字**，只包含定位信息：

```markdown
# 认知记忆索引

## 文件位置
- L3-L5: `memory/cognition/`
- L2情境: `memory/wiki/index.md`
- 边界: `memory/boundary.md`

## L3行为模式 (最新3条)
| 标题 | 关键词 | 置信度 | 更新 |
|------|--------|--------|------|
| 决策拖延 | 决策,拖延,周末 | 高 | 2024-01 |

## L4认知 (最新3条)
| 标题 | 关键词 | 置信度 | 更新 |
|------|--------|--------|------|
| 职业倦怠 | 工作,倦怠,转行 | 中 | 2024-01 |

## L5核心 (全部)
| 标题 | 关键词 |
|------|--------|
| 成长驱动 | 成长,意义,停滞恐惧 |

## 待验证队列 (Top 3)

*索引版本: 2024-01 | 条目: 12*
```

**索引设计原则**:
- 每层只显示最新3条 + 高优先级条目
- 用"关键词"替代详情描述
- 置信度快速判断可用性
- 详情通过 `memory_search` 按需检索

### 索引定位格式

每条记忆条目在索引中的定位信息：


## 五、提炼流程规范

### Ingest工作流（融合wiki-builder）

```
1. 读 (Read)
   - 收集 L2 待验证条目
   - 关联已有 L3-L5 认知
   
2. 讨论 (Reflect)
   - 执行反幻觉校验
   - 生成/修正假设
   
3. 写 (Write)
   - 提炼结论或更新待验证
   - 更新条目状态
   
4. 更新索引 (Index)
   - 更新 memory/index.md
   - 更新相关层级索引
   
5. 更新关联 (Link)
   - 建立跨层引用
   - 更新与 wiki-builder 的双向链接
   
6. 追加日志 (Log)
   - 记录操作到 memory/log.md
   - 记录提炼过程和依据
```

### 提炼质量控制（关键挑战2）

#### 反幻觉校验四规则

**规则1: 小样本检验**
```
✗ 禁止: 用户说了1次 → 提炼为"用户喜欢X"
✓ 必须: 标记"需多次验证"，待积累≥3次证据
```

**规则2: 情境依赖检验**
```
✗ 禁止: 天冷时说"不想出门" → "用户不喜欢出门"
✓ 必须: "天冷时倾向室内活动"
```

**规则3: 言行一致检验**
```
✗ 禁止: 用户说"想减肥" → "用户决心减肥"
✓ 必须: 检查历史执行率，降级为"有意愿但执行力待观察"
```

**规则4: 可逆性表述**
```
✗ 禁止: "用户总是..." "用户从不..."
✓ 必须: "在X情境下倾向于..." "现有观察中未出现..."
```

#### 校验执行Prompt

```markdown
## 反幻觉校验

### 待校验提炼
"[原始提炼结论]"

### 检查项
1. 验证次数 ≥ 3？
   - 当前: X次
   - [通过/不通过]

2. 有情境限定？
   - [有/无]
   - 如无，添加限定

3. 历史行为一致？
   - [一致/矛盾/待查]

4. 使用绝对化词汇？
   - [是/否]
   - 如是，改为可逆表述

### 结论
[安全提炼/需要修正/不能提炼]
```

### 用户确认机制

**需要确认的场景**:
- 提炼触及 L4-L5（深层认知）
- 结论可能让用户感到被"评判"
- 涉及敏感话题（金钱、健康、人际关系）

**不需要确认的场景**:
- L3 行为观察
- 情境事件记录
- 日常偏好记录

**确认方式**:
- 简单插入: "我注意到你... 这是准确的吗？"
- 选项确认: "基于观察，你更倾向于A还是B？"
- 延迟确认: "关于这个我有些假设，等积累更多证据再和你确认"

## 七、提炼循环触发机制

> 本章节说明提炼循环在什么时机触发，以及与现有触发机制的协同关系。

### 对话结束时的提炼循环触发

**约束**: 深度对话结束才触发，不是每条消息都触发

**操作清单**:
```markdown
### 深度对话结束
□ 执行提炼循环自检（见2.5节）
□ 检测新信号
□ 检查矛盾
□ 评估证据积累
□ 决定是否需要更新
□ 决定更新层级（L3/L4/L5）
□ 需要用户确认时，在下次对话开始时轻提示
```

**触发判断标准**：
- 用户表达了新的行为模式、偏好或价值观
- 用户对某事做出了评价或选择
- 用户分享了新的经历或想法
- 用户纠正了之前的理解

**不触发的情况**：
- 纯查询性问题（用户只是问问题，没有表达自我）
- 确认性对话（用户确认之前的信息）
- 情绪性爆发（需要冷静后再评估）

### Heartbeat 触发

**约束**: 30分钟一次，要快，不能跑重任务

**操作清单**:
```markdown
### 快速扫描 (<5分钟)
□ 扫描 pending.md 中的待验证条目
□ 处理验证进度 ≥2/3 的条目
□ 检查新信号是否积累到阈值
□ 更新索引（只改变化部分）
□ 记录日志（批量）
```

### Calendar 触发

**约束**: 可以跑重任务，产出要存文件

**操作清单**:
```markdown
### 定期任务
□ 周报: 扫描本周新条目，更新索引
□ 月报: 深度提炼，认知更新
□ 季度: 滚动窗口检查，归档

### Lint 健康检查
□ 矛盾检测: 检测认知矛盾，登记到 pending.md
□ 孤儿记忆: 找出无关联条目
□ 缺失关联: 识别应该关联但未关联的条目
□ 提炼循环审计: 检查待验证队列的进展
```

**实际价值**:
1. **快速定位**: 语义搜索+关键词双重匹配
2. **同义词扩展**: "决策"可匹配"选择""决定""拍板"
3. **跨语言**: 中文语义+英文关键词

**设计原则**:
```markdown
keywords: 决策,选择,决定,拍板,拖延,冷静期
```

## 九、淘汰与归档规范

### 权重管理（关键挑战3）

**定性权重替代数值权重**:
```
H (高权重):
- 3次以上验证确认
- 用户主动确认
- 涉及L4-L5

M (中权重):
- 2-3次验证
- 无反例
- L3行为

L (低权重):
- 1次观察
- 待验证
- 可能被覆盖
```

**时间衰减规则**:
```
活跃条目:
- 持续使用，持续验证
- 6个月无更新 → 检查是否归档

待验证条目:
- 3个月无进展 → 降级或归档
- 出现反例 → 立即降级

已归档条目:
- 保留原因记录
- 可恢复，不删除
```

### L2情境层滚动窗口（关键挑战4）

**实现方式**:

```markdown
## 滚动窗口规则

### 保留策略
- 活跃: 最近6个月
- 过渡: 6-12个月，降为低优先级
- 归档: 超过12个月，移入archive/

### 触发时机
- 每月1日检查
- 或条目总数超过阈值时触发

### 操作流程
1. 扫描 memory/wiki/index.md
2. 识别超过6个月的条目
3. 更新状态为"过渡"
4. 超过12个月，移动至archive/
5. 更新索引
6. 记录日志
```

**实际效果**:
- 旧事件不丢失，只是降低检索优先级
- 保持索引精简
- 可恢复，必要时可回溯

### 归档操作

```markdown
---
归档时间: 2024-01-15
归档原因: 超过12个月
合并至: L3-B-202401-002
原始ID: L2-2023-001
---

归档时保留:
- 原始内容
- 归档原因
- 合并目标（如有）
- 操作日志链接
```

## 十一、待验证队列规范

### pending.md 的作用

`pending.md` 是提炼循环的"工作台"——存放那些还没完全确认、但值得追踪的认知线索。

**什么时候写入 pending.md**：

| 情况 | 处理 |
|-----|------|
| 新信号被检测到，但证据不足 | 写入 pending.md，标记 1/3 |
| 新信号与旧认知矛盾 | 写入 pending.md，标记"矛盾" |
| 旧认知出现反例 | 写入 pending.md，标记"存疑" |

### pending.md 格式

```markdown
# 待验证队列

## 活跃待验证

### P-001 | 决策冷静期需求 | 1/3
- **类型**: 新信号验证
- **假设**: 用户在重大决策前需要冷静期
- **证据**:
  - [x] 2024-01-15: 讨论保险方案，说"我回去想想"
  - [ ] 还需要2次独立观察
- **下次验证**: 下次遇到决策场景时观察

### P-002 | 沟通风格矛盾 | 待验证
- **类型**: 认知矛盾
- **旧认知**: 用户喜欢直接反馈
- **新信号**: 用户在某些情境下回避冲突
- **可能解释**: 
  1. 情境依赖（公开vs私下场合）
  2. 涉及话题的敏感性不同
  3. 旧认知不准确
- **验证方向**: 区分场合观察

---

## 已完成（可归档）

### P-003 | 拖延但靠谱 | 已确认 → L3-B-005
- **最终结论**: 用户会拖延但最终会交付，属于"慢性子但靠谱"型
- **确认时间**: 2024-02-01
- **合并至**: behavior.md
```

### 验证进展管理

```
验证进度计算：
- 每获得1次独立观察 → 更新 pending.md 进度
- 进度达到 3/3 → 触发更新决策
- 超过3个月无进展 → 降级或归档
- 出现反例 → 立即标记，暂停验证
```

### 与 Lint 健康检查的协同

```
每月 Lint 检查时：
□ 扫描 pending.md
□ 识别超过3个月无进展的条目
□ 识别出现反例的条目
□ 更新条目状态（降级/归档/激活）
□ 记录检查日志
```

## 十二、线索词机制详解

### 线索词的真正价值

**不是冗余的**:
1. **语义增强**: 补充语义搜索可能遗漏的同义词
2. **上下文提示**: 帮助快速理解条目含义
3. **跨语言桥接**: 中文语义+英文标签
4. **精确匹配**: 当需要精确查找时

**设计示例**:
```markdown
## 决策冷静期
keywords: 决策,选择,决定,拍板,拖延,冷静期,周末,重大决定
         ↑核心   ↑同义  ↑近义  ↑反义  ↑情境  ↑时间限定
```

### 线索词生成规则

```markdown
## 线索词生成
每个条目至少包含:
1. 核心词 (1-2个): 最本质的描述
2. 同义词 (1-3个): 语义相近的词
3. 相关词 (1-3个): 情境相关的词
4. 限定词 (0-2个): 时间/条件限定

禁止:
✗ 过长 (超过10个)
✗ 无关词 (强行关联)
✗ 模糊词 (可能,大概)
```

## 十一、Lint 健康检查

### 检查项目

```markdown
## Lint 检查清单

### 1. 矛盾标注
- 检测同层冲突认知
- 例: "用户喜欢主动" vs "用户习惯被动"
- 处理: 标记冲突，待验证

### 2. 孤儿记忆
- 检测无关联的条目
- 例: 某行为模式无任何关联事件
- 处理: 建立关联或归档

### 3. 缺失关联
- 检测应该关联但未关联
- 例: L4价值观未关联任何L3行为
- 处理: 补充关联

### 4. 悬空引用
- 检测引用了不存在的条目
- 处理: 清理或修复引用

### 5. 索引一致性
- 检测索引与实际内容不一致
- 处理: 重建索引
```

### 检查频率

| 检查类型 | 频率 | 执行者 |
|---------|------|-------|
| 悬空引用 | 每次写入时 | 自动 |
| 索引一致性 | 每次写入后 | 自动 |
| 矛盾标注 | Calendar周任务 | 自动 |
| 孤儿记忆 | Calendar月任务 | 自动 |
| 缺失关联 | Calendar季度任务 | 需确认 |

### 日志原则

1. **操作必记**: 每次写入/更新/归档都要记录
2. **记录原因**: 不仅记做了什么，记为什么做
3. **可追溯**: 能从日志重建认知变化过程
4. **不记详情**: 详情在原条目，日志只是索引

## 十三、关键设计决策汇总

### 挑战1: 索引vs详情平衡
- **方案**: 主索引 <500字，始终加载
- **机制**: 二级检索，索引定位+详情按需
- **验证**: 每条记忆都有索引定位信息

### 挑战2: 提炼质量控制
- **方案**: 四规则反幻觉校验
- **机制**: 校验Prompt+用户确认机制
- **验证**: 提炼必须通过校验才能写入

### 挑战3: 记忆膨胀控制
- **方案**: 定性权重+时间衰减+滚动窗口
- **机制**: 6个月活跃/12个月归档
- **验证**: L2情境层有滚动窗口实现

### 挑战4: 与现有文件兼容
- **方案**: 分层迁移+独立维护
- **机制**: USER.md→认知层，MEMORY.md→wiki
- **验证**: 保留过渡期，不强制删除

### 挑战5: SOUL.md与L5区分
- **方案**: 职责分离
- **机制**: SOUL.md是Agent，L5是用户
- **验证**: 两者内容不重叠

### 挑战6: 线索词价值
- **方案**: 语义增强+同义词扩展
- **机制**: 每条记忆附带关键词标签
- **验证**: 辅助语义搜索，不是主力

## 十四、自动捕获 Hook 系统 [v2新增]

### 设计动机

v1 的提炼循环需要手动触发或在特定时机（深度对话结束、Heartbeat、Calendar）触发，存在两个问题：

1. **捕获不自动**——新观察需要人工判断是否值得记录，容易遗漏
2. **流程不连贯**——从观察到提炼之间的链路是断裂的，没有生命周期管理

v2 引入 6 个生命周期 Hook，借鉴 AgentMemory 的自动捕获机制但更轻量——不引入额外进程，复用平台现有的事件机制。

### Hook 总览

```
┌─────────────────────────────────────────────────────────────┐
│                   认知记忆生命周期                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ① on_session_start                                        │
│     读取 index + 加载认知层                                 │
│            │                                                │
│            ▼                                                │
│  ② on_new_observation                                      │
│     检测新信号 → 写入 pending 或 wiki/entries               │
│            │                                                │
│            ▼                                                │
│  ③ on_contradiction_detected                               │
│     标记待验证 → 不覆盖旧认知                               │
│            │                                                │
│            ▼                                                │
│  ④ on_evidence_accumulated                                 │
│     检查证据阈值 → 触发提炼                                 │
│            │                                                │
│            ▼                                                │
│  ⑤ on_session_end                                          │
│     执行提炼循环自检 → 更新索引                             │
│            │                                                │
│            ▼                                                │
│  ⑥ on_periodic_lint                                        │
│     Calendar 触发 → 执行健康检查                            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### Hook 1: on_session_start

**触发条件**：会话开始时自动触发

**执行逻辑**：

```markdown
## on_session_start 执行清单

1. 读取 brain/index.md（始终加载，<500 token）
2. 加载认知层摘要:
   - behavior.md 中的高置信度条目
   - cognition.md 中的最新条目
   - core.md 中的全部条目
3. 检查 pending.md 中的待验证条目
4. 恢复上次会话上下文（如有）
5. 预加载相关认知（使用 retrieval-engine 按主题预检索）
```

**时间限制**：<5秒

**产出**：
- 认知层摘要加载到上下文
- 待验证队列状态
- 预检索结果（如有明确主题）

**平台适配**：

| 平台 | 触发方式 | 加载方式 |
|------|----------|----------|
| **扣子** | 对话开始时自动执行 | read_file + memory_search |
| **Claude Code** | 脚本启动时 | 直接文件读取 + ripgrep |
| **Cursor** | 打开项目时 | 文件读取 |
| **通用** | 手动触发 | 文件读取 |

### Hook 2: on_new_observation

**触发条件**：对话中检测到新的认知信号

**信号检测标准**：

```markdown
## 新信号检测维度

✓ 行为模式：遇到X时会做Y（之前未观察到）
✓ 偏好表达：对X的喜好/厌恶（之前未记录）
✓ 价值观流露：提到"我觉得应该X"（与现有价值观一致或矛盾）
✓ 决策倾向：选择A而不是B（揭示了优先级）
✓ 自我认知：用户对自己的评价

✗ 一次性情绪 → 不记录
✗ 纯查询性对话 → 不记录
✗ 情绪性爆发 → 标记但不写入
```

**执行逻辑**：

```markdown
## on_new_observation 执行清单 [v2.2 更新默认行为]

1. 检测新信号类型和行为模式
2. governance.validate(新观察) → 校验质量
   - pass → 进入步骤3
   - fail → 丢弃或降级
   - needs_review → 进入步骤3并标记"待验证"
3. 判断写入位置 [v2.2 默认先写 pending/]:
   - L2 情境事件 → wiki/entries/L2-YYYY-XXX.md（保持 v2.1）
   - **新信号/待验证 → pending/{日期-主题}.md [v2.2 默认]**
   - 已确认的 L3+ 提炼 → cognition/behavior.md（用户明确确认后）
   - 矛盾/待验证 L2+ → pending.md（v2.1 待验证队列）
4. [v2.2 新增] 同步 append 一行到 SESSION-STATE.md（WAL 写入）
5. 更新 index.md 索引
6. 追加 log.md
```

**时间限制**：<3秒（不能打断对话节奏）

**v2.2 行为变更说明**：

| 行为 | v2.1 | v2.2 默认 | v2.2 可关闭 |
|------|------|-----------|-------------|
| 新信号写入位置 | 直接进 cognition/ 或 pending.md | 先写 `pending/{日期-主题}.md` | config `two_stage_workflow.enabled = false` 可回退 |
| 写入 cognition/ 的时机 | on_new_observation 时 | 待 lint promote 或用户明确确认 | 同 v2.1 |
| 同步写 SESSION-STATE.md | 无 | **默认开启** | 平台不支持文件时降级 |

> 详见主 SKILL.md "核心机制 2：先毛坯后蒸馏" 的完整规范。

**产出**：
- 新条目写入对应文件（v2.2 默认是 `pending/`）
- SESSION-STATE.md 工作区更新（v2.2）
- 索引更新
- 操作日志

### Hook 3: on_contradiction_detected

**触发条件**：新观察与现有认知存在矛盾

**矛盾检测逻辑**：

```markdown
## 矛盾检测流程

1. 新观察写入时，自动比对现有认知:
   - 检查 behavior.md 中的行为模式
   - 检查 cognition.md 中的价值观
   - 检查 core.md 中的核心特质

2. 矛盾类型判断:
   - 情境性矛盾 → 不同情境下表现不同
   - 观察性矛盾 → 两次观察不一致
   - 实质性矛盾 → 与核心认知冲突

3. 处理策略:
   - 情境性 → 降级表述，添加情境限定
   - 观察性 → 进入待验证队列
   - 实质性 → 标记"待验证"，不覆盖旧认知
```

**执行逻辑**：

```markdown
## on_contradiction_detected 执行清单

1. 识别矛盾类型（情境性/观察性/实质性）
2. governance.validate(矛盾条目) → 校验
3. 根据矛盾策略处理:
   - mark_and_keep → 两方保留，标记矛盾关系
   - user_decides → 记录矛盾，下次对话时询问
   - new_overwrites → 用新认知替换旧认知
4. 更新相关条目的 contradicts 字段
5. 写入 pending.md（如需要进一步验证）
6. 更新 index.md
7. 追加 log.md
```

**时间限制**：<5秒

**产出**：
- 矛盾标记写入相关条目
- 待验证条目更新
- 索引和日志更新

### Hook 4: on_evidence_accumulated

**触发条件**：某个待验证条目的证据数量增加

**触发时机**：
- on_new_observation 写入了与 pending 条目相关的观察
- Heartbeat 扫描发现新的相关证据
- 用户明确确认了某个观察

**执行逻辑**：

```markdown
## on_evidence_accumulated 执行清单

2. 检查是否达到证据阈值:
   - L3: ≥3 次独立观察

   - L5: ≥3 次独立观察 + 无反例 + 跨情境一致

4. 未达到阈值:
   - 继续积累，更新进度
5. 更新 index.md
6. 追加 log.md
```

**时间限制**：<5秒

**产出**：
- 待验证条目进度更新
- 可能的层级提升
- 索引和日志更新

## 十五、4 层压缩管线 [v2新增]

### 设计动机

v1 的记忆只增不减，缺少压缩合并机制。随着使用时间增长，认知文件会膨胀，导致：
- Token 超限，无法完整加载
- 信息冗余，相同模式多次记录
- 检索效率降低，噪音增加

v2 引入 4 层压缩管线，借鉴 AgentMemory 的 raw → compressed → merged → long-term 模式，但与 agent-brain 的 5 层架构对应。

### 压缩管线与 5 层架构的关系

**关键理解**：4 层压缩管线是**写入管线**，5 层架构是**存储架构**。

```
4层压缩管线（怎么从对话到认知）     5层架构（认知存在哪里）

L0 原始观察                       → L1 状态层（会话内）
  ↓ 自动捕获                        （不持久化）
L1 压缩观察                       → L2 情境层（事件记录）
  ↓ on_session_end
L2 跨会话合并                     → L3 行为层（行为模式）
  ↓ on_evidence_accumulated
L3+ 长期认知                      → L4 认知层 + L5 核心层
  ↓ 提炼循环确认
```

**管线处理"怎么从对话到认知"，架构处理"认知存在哪里"。**

### L0 → L1：自动捕获与压缩

**L0 原始观察**：对话中的每条有价值信息

```markdown
## L0 原始观察格式

在对话过程中，Agent 识别到有价值的信息时，立即记录:

### 观察记录
- 时间: 2024-02-01 14:30
- 情境: 讨论项目排期
- 内容: 用户说"这个不急，下周再说"
- 信号类型: 决策倾向
- 关联: 可能与"决策冷静期"模式相关
```

**L1 压缩观察**：同会话内相关观察合并

**触发**：`on_session_end`

**执行逻辑**：

```markdown
## L0 → L1 压缩流程

1. 收集本次会话的所有 L0 原始观察
2. 按主题/关键词分组
3. 同组内的观察合并:
   - 重复信息 → 去重
   - 互补信息 → 合并为完整描述
   - 矛盾信息 → 标记待验证
4. 生成 L1 压缩观察:
   - 一条 L1 = 同组 L0 的合并摘要
   - 附带原始 L0 的引用
5. 写入 wiki/entries/ 或 pending.md
```

**示例**：

```
L0 观察 (3条):
  - "这个不急，下周再说" (14:30)
  - "我需要想想哪个方案好" (14:45)
  - "先放放，不着急决定" (15:10)

L1 压缩观察 (1条):
  "本次会话中，用户3次表达延迟决策意愿，
   与'决策冷静期'模式一致。
   证据: 3/3，进度更新"
```

---

### L1 → L2：跨会话合并

**触发**：`on_evidence_accumulated`（当新观察与历史观察匹配时）

**执行逻辑**：

```markdown
## L1 → L2 合并流程

1. 检测新 L1 观察是否与历史 L1 观察属于同一模式
2. 匹配条件:
   - 关键词重叠 ≥ 50%
   - 语义相似度 ≥ 0.7（人工判断或平台语义搜索）
   - 属于同一认知维度（行为/偏好/价值观）
3. 合并策略:
   - 不同会话的相同模式 → 合并为跨会话观察
   - 补充情境差异 → 添加情境限定
   - 矛盾观察 → 标记待验证
4. 生成 L2 跨会话合并:
   - 一条 L2 = 多个 L1 的跨会话综合
   - 附带所有 L1 的引用
   - 标注验证进度 (如 2/3)
5. 更新 pending.md 或写入认知层
```

**示例**：

```
L1 观察 (3个不同会话):
  会话A: "用户3次表达延迟决策意愿"
  会话B: "用户说'我再想想'，2天后回复"
  会话C: "用户对3个选项要求对比分析后再决定"

L2 跨会话合并 (1条):
  "跨3个会话观察: 用户在非紧急决策场景下，
   一致性地表现出'冷静期'需求——不立即决定，
   需要思考时间（1-3天），且倾向详细分析。
   验证进度: 3/3，可提升至 L3"
```

---

### L2 → L3+：长期认知确认

**触发**：`on_evidence_accumulated` + 提炼循环确认

**执行逻辑**：

```markdown
## L2 → L3+ 确认流程

1. 检查证据阈值是否达标:
   - L3: ≥3 次独立观察
   - L4: ≥3 次独立观察 + 无反例 + 用户确认
   - L5: ≥3 次独立观察 + 无反例 + 跨情境一致 + 明确确认

2. 执行 governance.promote():
   - L2 → L3: 自动（可配置）
   - L2/L3 → L4: 需用户确认
   - L3/L4 → L5: 需明确确认

3. 确认后写入对应认知文件:
   - L3 → behavior.md
   - L4 → cognition.md
   - L5 → core.md

4. 压缩原始观察:
   - 保留摘要和引用
   - 原始 L0/L1 内容可归档
   - L2 wiki 条目保留但降低优先级
```

**示例**：

```
L2 跨会话合并:
  "跨3个会话观察: 用户在非紧急决策场景下，
   一致性地表现出'冷静期'需求"

governance.promote(L2-merged, L3):
  → validate: pass
  → 写入 behavior.md:
    "## 决策冷静期
     在非紧急决策场景下，用户需要1-3天冷静期，
     期间倾向详细分析而非立即决定。
     [证据: 3次独立观察，0反例]
     [来源: L2-2024-001, L2-2024-008, L2-2024-015]"
  → 归档原始观察
```

---

### 压缩管线与 Token 管理

```
L0 原始观察 (每条 ~100-200 token)
  ↓ 压缩 (去重+合并)
L1 压缩观察 (每条 ~80-150 token，减少30-40%)
  ↓ 合并 (跨会话综合)
L2 跨会话合并 (每条 ~150-250 token，但条目数大幅减少)
  ↓ 确认 (提炼+归档原始)
L3+ 长期认知 (每条 ~100-200 token，原始观察已归档)
```

**Token 节约效果**：

| 阶段 | 条目数 | 总 Token | 节约率 |
|------|--------|----------|--------|
| L0 原始 | 30条 | ~4500 | — |
| L1 压缩 | 12条 | ~1440 | 68% |
| L2 合并 | 5条 | ~1000 | 78% |
| L3+ 认知 | 3条 | ~450 | 90% |

## 十六、Token 预算管理 [v2新增]

### 设计动机

v1 没有_token 预算管理，认知文件可能无限膨胀。当 behavior.md 超过 2000 token 时，加载它会消耗大量上下文窗口，留给对话的空间就少了。

v2 引入三层 Token 预算管理，确保记忆系统不会"吃掉"上下文。

### 每文件 Token 上限

| 文件 | Token 上限 | 当前估计 | 超限处理 |
|------|----------|----------|----------|
| `index.md` | 500 | ~300 | 提取摘要，移详情到 wiki/entries |
| `behavior.md` | 2000 | ~1200 | 触发压缩管线，合并同类项 |
| `cognition.md` | 1500 | ~800 | 触发压缩管线，提炼精简 |
| `core.md` | 800 | ~300 | 触发压缩管线，仅保留最高置信度 |
| `wiki/index.md` | 1000 | ~500 | 归档旧条目 |
| `pending.md` | 1500 | ~600 | 归档已完成/过期条目 |

### 超限压缩流程

```markdown
## 文件超限压缩流程

1. 检测: lint 或写入时检查文件 token 估算
2. 判断: 当前 token > 上限?
3. 触发压缩:
   a. 识别同类项（关键词重叠 ≥ 50% 的条目）
   b. 合并同类项:
      - 相同模式 → 合并为一条，附证据引用
      - 情境限定不同 → 保留为子条目
      - 矛盾条目 → 不合并，标记待验证
   c. 提取摘要:
      - 每条保留核心描述（1-2句）
      - 详情移至 wiki/entries/
      - 在条目中添加引用链接
   d. 归档原始:
      - 被压缩的原始内容移入 archive/
      - 保留可恢复标记
4. 验证: 压缩后 token < 上限?
   - 是 → 完成
   - 否 → 进一步压缩（降级低置信度条目）
5. 更新 index.md 和 log.md
```

### 检索 Token 预算

详见 `modules/retrieval-engine/SKILL.md` 第四章

核心规则：
- 每次检索默认 ≤ 2000 token
- 先返回索引摘要（~200 token）
- 按需加载详情
- 超预算按置信度截断

### Token 估算工具

```markdown
## Token 快速估算（Agent 内置）

### 方法1: 字符计数法
- 中文: 字符数 × 1.5 ≈ token 数
- 英文: 词数 × 1.0 ≈ token 数
- 混合: 取加权和

### 方法2: 行数估算法
- 空行: 0 token
- 短行(<30字符): ~10-20 token
- 中行(30-100字符): ~30-60 token
- 长行(>100字符): ~60-150 token

### 方法3: 段落估算法
- 索引条目: ~30 token/条
- 行为模式: ~150-250 token/条
- 情境事件: ~200-500 token/条
- 价值观/核心: ~100-200 token/条
```

### 平台适配

| 平台 | Token 估算方式 | 压缩触发 |
|------|---------------|----------|
| **扣子** | 对话中人工估算 | on_session_end 检查 |
| **Claude Code** | 脚本自动计算 | git pre-commit hook |
| **Cursor** | 内联估算 | 保存文件时检查 |
| **通用** | 字符计数 | 手动触发 |
