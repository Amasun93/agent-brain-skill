# Retrieval Engine Skill

**混合检索引擎**：三路融合检索 + Token 预算管理，让记忆"取得到、取得准、取得起"。

---

## 一、设计动机 [v2新增]

### v1 的检索短板

agent-brain v1 的检索完全依赖平台的 `memory_search`，存在三个问题：

| 问题 | 表现 | 后果 |
|------|------|------|
| **单一路径** | 只有语义检索，没有关键词和关联检索 | 精确查找容易漏，关系追踪做不了 |
| **无 Token 预算** | 检索结果可能撑爆上下文 | 索引加载 + 检索结果 + 对话内容超出窗口 |
| **无策略表** | 所有查询用同一套检索逻辑 | "上次讨论的JWT方案"和"用户对工作的态度"用相同方式检索，效率低 |

### v2 的检索方案

借鉴 AgentMemory 的 RRF（Reciprocal Rank Fusion）方案，但更轻量——不引入额外向量数据库，复用平台现有能力：

```
┌─────────────────────────────────────────────────────────────┐
│                    三路融合检索                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  路径1: 关键词检索 ──┐                                     │
│  (BM25风格)          │                                     │
│                      ├──→ RRF融合排序 ──→ Token预算裁剪 ──→ 结果 │
│  路径2: 语义检索 ────┤                                     │
│  (向量/平台)         │                                     │
│                      │                                     │
│  路径3: 关联检索 ────┘                                     │
│  (图谱/交叉引用)                                           │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 二、三路检索详解 [v2新增]

### 路径1：关键词检索（BM25 风格）

**核心思路**：用关键词标签 + 文件名做精确匹配，适合"我知道我要找什么"的场景。

**实现方式**：

| 平台 | 实现方式 | 具体操作 |
|------|----------|----------|
| **扣子** | `read_file` + 关键词匹配 | 读取 `index.md`，在关键词列中精确匹配 |
| **Claude Code** | `ripgrep` | `rg -i "关键词" brain/` 全文搜索 |
| **Cursor** | 内置搜索 | Ctrl+Shift+F 全局搜索 |
| **通用** | 文件遍历 | 逐文件 `read_file`，检查 keywords 字段 |

**执行逻辑**：

```markdown
## 关键词检索流程

1. 解析查询 → 提取关键词
   - 输入: "上次讨论的那个JWT方案"
   - 提取: ["JWT", "方案"]

2. 扫描 index.md → 匹配关键词列
   - 遍历所有条目的 keywords 字段
   - 匹配度 = 命中关键词数 / 查询关键词数

3. 返回匹配条目列表
   - 按匹配度降序排列
   - 附带层级、置信度信息
```

**适用场景**：
- 精确查找："那个JWT方案"
- 主题定位："保险相关的讨论"
- 名称检索："L2-2024-015"

### 路径2：语义检索（向量）

**核心思路**：用语义理解做模糊匹配，适合"我知道大概意思但说不出关键词"的场景。

**实现方式**：

| 平台 | 主方案 | 回退方案 |
|------|--------|----------|
| **扣子** | `memory_search`（平台内置语义搜索） | 关键词检索（路径1） |
| **Claude Code** | 内置语义搜索 | `ripgrep` + 关键词 |
| **Cursor** | 内置搜索（混合语义） | 全文搜索 |
| **通用** | 关键词检索（路径1） | 文件遍历 + 相似度 |

**扣子平台 memory_search 使用规范**：

```markdown
## memory_search 参数配置

### 基础检索
- query: 用自然语言描述查询意图
- focus: "balanced"（默认，均衡搜索）
- max_results: 10（默认）

### 侧重对话记录
- focus: "prefer_messages"
- 适用: 查找"用户说过什么"

### 侧重文件内容
- focus: "prefer_files"
- 适用: 查找"记录在哪个文件"

### 时间限定
- start_time / end_time: RFC3339 格式
- 适用: 查找"最近一周的讨论"
```

**适用场景**：
- 语义理解："用户对工作的态度"
- 模糊查询："那个关于什么的选择"
- 情感检索："用户提到压力的记录"

### 路径3：关联检索（图谱）

**核心思路**：基于索引中的交叉引用和线索词做关系追踪，适合"找到A后想知道和A相关的所有东西"。

**实现方式**：

| 平台 | 实现方式 | 数据来源 |
|------|----------|----------|
| **扣子** | `read_file` 读索引 → 解析交叉引用 | `index.md` + `wiki/index.md` |
| **Claude Code** | `ripgrep` 搜索引用标记 | `[[L2-xxx]]` 格式的交叉引用 |
| **Cursor** | 内置引用跳转 | Markdown 链接 |
| **通用** | 文件解析 | 条目中的关联字段 |

**执行逻辑**：

```markdown
## 关联检索流程

1. 起点：一个已知条目 ID（如 L3-B-001）
2. 读取该条目的关联字段:
   - related: [L2-2024-001, L2-2024-008]
   - contradicts: [L3-B-003]
   - supports: [L4-C-002]

3. 扩展检索:
   - 一跳：读取直接关联的条目
   - 二跳：读取关联条目的关联（可选，按需）

4. 返回关联图谱（扁平列表）
   - 每条附带：关系类型、跳数、置信度
```

**交叉引用格式**：

```markdown
## 条目中的关联标记

### 显式关联
- related: L2-2024-001, L2-2024-008    ← 直接关联
- contradicts: L3-B-003                  ← 矛盾关系
- supports: L4-C-002                     ← 支撑关系
- evolved_from: L3-B-001                 ← 演化来源

### 隐式关联（线索词匹配）
- keywords 中的重叠词 → 可能的关联
- 同一时间段内的条目 → 可能的情境关联
```

**适用场景**：
- 关系追踪："这个行为模式关联哪些事件"
- 影响分析："改了这个认知，会影响哪些条目"
- 全景查看："围绕这个主题的所有记录"

## 三、RRF 融合排序 [v2新增]

### RRF 算法

**Reciprocal Rank Fusion**：不依赖分数，只依赖排名，三路结果公平融合。

```
RRF_score(entry) = Σ(1 / (k + rank_i))

其中:
- k = 60（标准常数，抑制头部条目的过度优势）
- rank_i = 该条目在第 i 路检索中的排名
- 未出现在某路结果中的条目，该路贡献为 0
```

### 融合流程

```
┌─────────────────────────────────────────────────────────────┐
│  输入: 用户查询                                              │
└─────────────────────────────────────────────────────────────┘
                          │
            ┌─────────────┼─────────────┐
            │             │             │
            ▼             ▼             ▼
     关键词检索      语义检索       关联检索
     (路径1)        (路径2)        (路径3)
            │             │             │
            ▼             ▼             ▼
     排名列表 R1     排名列表 R2    排名列表 R3
            │             │             │
            └─────────────┼─────────────┘
                          │
                          ▼
              ┌───────────────────────┐
              │  RRF 融合             │
              │  score = Σ 1/(k+rank) │
              │  k = 60               │
              └───────────────────────┘
                          │
                          ▼
              ┌───────────────────────┐
              │  Token 预算裁剪       │
              │  按置信度截断          │
              └───────────────────────┘
                          │
                          ▼
              ┌───────────────────────┐
              │  最终结果列表          │
              │  (ID + 摘要 + 置信度) │
              └───────────────────────┘
```

### 手动 RRF 实现（无代码依赖）

```markdown
## RRF 融合步骤

1. 收集三路结果:
   - R1 = 关键词检索的排名列表
   - R2 = 语义检索的排名列表
   - R3 = 关联检索的排名列表

2. 计算每个条目的 RRF 分数:
   - 对每个条目 entry:
     - rank1 = entry 在 R1 中的排名（未出现则为 ∞，贡献 0）
     - rank2 = entry 在 R2 中的排名
     - rank3 = entry 在 R3 中的排名
     - score = 1/(60+rank1) + 1/(60+rank2) + 1/(60+rank3)

3. 按 score 降序排列

4. Token 预算裁剪（见第四章）
```

### RRF 示例

```
查询: "用户对决策的态度"

R1（关键词 "决策"）:
  1. L3-B-001 决策冷静期
  2. L2-2024-015 保险方案讨论
  3. L3-B-005 拖延但靠谱

R2（语义搜索）:
  1. L3-B-005 拖延但靠谱
  2. L3-B-001 决策冷静期
  3. L4-C-002 谨慎价值观

R3（关联: 从 L3-B-001 出发）:
  1. L3-B-001 决策冷静期
  2. L2-2024-001 首次讨论保险
  3. L4-C-002 谨慎价值观

RRF 计算:
  L3-B-001: 1/(60+1) + 1/(60+2) + 1/(60+1) = 0.0492  ← 最高
  L3-B-005: 1/(60+3) + 1/(60+1) + 0          = 0.0328
  L4-C-002: 0         + 1/(60+3) + 1/(60+3)   = 0.0323
  L2-2024-015: 1/(60+2) + 0 + 0               = 0.0161
  L2-2024-001: 0 + 0 + 1/(60+2)               = 0.0161

最终排序: L3-B-001 > L3-B-005 > L4-C-002 > L2-2024-015 ≈ L2-2024-001
```

## 四、Token 预算管理 [v2新增]

### 为什么需要 Token 预算

没有预算管理时，检索结果可能无限膨胀：

```
index.md (500 token)
+ behavior.md (2000 token)
+ cognition.md (1500 token)
+ 3个 L2 详情 (各 500 token)
+ 对话上下文 (3000 token)
= 8500+ token → 可能撑爆上下文
```

### Token 预算机制

**三层预算控制**：

```
┌─────────────────────────────────────────────────────────────┐
│  检索预算: 单次检索 ≤ 2000 token                            │
│  ─────────────────────────────                              │
│  先返回索引摘要（~200 token）                                │
│  按需加载详情（每条 ~200 token）                              │
│  超预算按置信度截断                                          │
├─────────────────────────────────────────────────────────────┤
│  文件预算: 每个认知文件有上限                                │
│  ─────────────────────────────                              │
│  index.md      ≤ 500 token                                  │
│  behavior.md   ≤ 2000 token                                 │
│  cognition.md  ≤ 1500 token                                 │
│  core.md       ≤ 800 token                                  │
│  超限 → 触发压缩管线（见 cognitive-memory SKILL.md）         │
├─────────────────────────────────────────────────────────────┤
│  会话预算: 整体上下文有上限                                  │
│  ─────────────────────────────                              │
│  始终加载: index.md (500)                                   │
│  按需加载: behavior/cognition/core + L2 详情                │
│  动态卸载: 不再需要的详情从上下文移除                        │
└─────────────────────────────────────────────────────────────┘
```

### 检索预算执行流程

```markdown
## 检索预算控制

### 第一步：返回摘要（~200 token）
每个检索结果只返回:
- ID
- 标题（一行）
- 置信度
- 关键词（3-5个）

### 第二步：按需加载详情
用户/Agent 需要更多信息时:
- 指定要加载的条目 ID
- 返回该条目的完整内容
- 扣减剩余 token 预算

### 第三步：超预算截断
当需要返回的详情超出 2000 token:
1. 按置信度排序（H > M > L）
2. 按层级排序（L5 > L4 > L3 > L2）
3. 依次填充，直到接近预算
4. 最后一条可能被截断（保留摘要部分）
5. 标记"[预算截断: 还有 N 条未加载]"
```

### Token 估算规则

```markdown
## Token 估算（中文为主）

经验值:
- 1 个中文字 ≈ 1.5 token
- 1 个英文单词 ≈ 1 token
- 1 行 Markdown ≈ 15-30 token（视内容）

快速估算:
- 索引条目摘要: ~30 token/条
- 行为模式条目: ~150-250 token/条
- 情境事件详情: ~200-500 token/条
- 价值观/核心认知: ~100-200 token/条
```

## 七、与 cognitive-memory 的协作 [v2新增]

### 检索引擎在认知流程中的位置

```
ingest → wiki-builder → cognitive-memory → git-sync
              │               │
              └───────┬───────┘
                      │
              ┌───────┴───────┐
              │               │
         retrieval-engine  memory-governance
         (怎么取)          (怎么保证对)
```

**检索引擎不改变认知层的存储结构，只改变"怎么取"的方式。**

### 协作场景

| 场景 | cognitive-memory 做什么 | retrieval-engine 做什么 |
|------|------------------------|------------------------|
| **新信号检测** | 判断是否有新认知信号 | 检索相关已有认知，提供比对基础 |
| **矛盾检测** | 判断新信号是否矛盾 | 三路检索相关认知，确保不遗漏 |
| **证据积累** | 计算验证进度 | 关联检索：找所有相关观察 |
| **提炼更新** | 执行更新决策 | 提供影响范围分析 |
| **待验证队列** | 管理 pending.md | 关联检索：找相关证据 |
| **Lint 检查** | 检测矛盾/孤儿/悬空 | 关联检索：验证引用完整性 |

### 检索触发时机

```markdown
## 自动检索触发

### on_session_start
- 加载 index.md（始终）
- 关键词检索: 根据上次会话主题，预加载相关条目摘要
- Token 预算: 500

### on_new_observation
- 语义检索: 查找与新观察相关的已有认知
- 关联检索: 查找与当前情境关联的历史事件
- Token 预算: 1000

### on_contradiction_detected
- 关键词检索: 精确查找矛盾涉及的条目
- 关联检索: 扩展查找所有受影响的条目
- Token 预算: 1500

### on_evidence_accumulated
- 关联检索: 收集所有相关证据
- Token 预算: 1500

### on_session_end
- 语义检索: 验证本次会话的认知更新是否完整
- Token 预算: 1000

### on_periodic_lint
- 关联检索: 检查所有交叉引用的完整性
- Token 预算: 2000
```

- 建议始终先读 index.md，再按需加载详情

## 九、检索性能优化 [v2新增]

### 索引优化

```markdown
## 索引优化策略

### 热点缓存
- 始终加载: index.md (<500 token)
- 高频条目: 在 index.md 中保留摘要
- 低频条目: 只保留 ID 和关键词

### 分区检索
- 精确查找: 只搜 index.md
- 语义理解: 先搜 index.md，再搜全量
- 关系追踪: 从 index.md 定位，再跳转详情

### 结果缓存
- 同一会话内的相同查询: 复用结果
- 相似查询: 复用部分结果，只刷新差异
```

### 检索降级策略

```markdown
## 检索降级（当平台能力不足时）

Level 0: 三路融合（全能力平台）
  → 关键词 + 语义 + 关联 → RRF 融合

Level 1: 双路融合（有语义搜索）
  → 语义 + 关键词 → RRF 融合

Level 2: 单路语义（仅语义搜索）
  → 语义检索 → 直接返回

Level 3: 纯关键词（无语义搜索）
  → 关键词检索 → 按匹配度排序

Level 4: 纯遍历（最低保障）
  → 文件遍历 → 字符串匹配
```
